## Recommended execution order

1. **002** — establishes the `--ease-out` token that plans 001, 004, 005, 006, and 007 all consume. Running it first avoids every other plan needing to fall back on its own defensive "add the token if missing" step.
2. **003** — fully independent (touch-hover gating, no shared tokens). Safe to run any time, including in parallel with the others.
3. **004** — adds `--duration-fast`/`--duration-base` and mass-adopts `--ease-out` across existing hover transitions. Best run after 002 so it's purely additive (durations only) rather than also deriving the easing token.
4. **001, 005, 006** — each independently consumes `--ease-out`; any order works once 002 has run. 006 (grid stagger) touches the same `[data-reveal]` neighborhood as 002, so running 002 first avoids any visual confusion when eyeballing the diff.
5. **007** — independent of everything except needing `--ease-out` (or it self-adds); also introduces its own new `--ease-in-out` token that nothing else depends on. Can run any time after 002.

## Dependencies

- Plans 001, 004, 005, 006, 007 each have a defensive first step: "add `--ease-out` to `:root` if it isn't already there." This makes every plan independently runnable regardless of order, but running 002 first means only 002 actually adds it — every later plan's check will find it already present and skip re-adding.
- No plan depends on another plan's HTML/JS changes — only on the shared CSS token(s), which are additive and idempotent.
- If a plan's "Boundaries" section says to STOP on drift (e.g. a cited line doesn't match), that means an earlier plan in this set already changed that code in a way this plan didn't anticipate — reconcile by re-reading the current file state before continuing, rather than forcing the original snippet.
